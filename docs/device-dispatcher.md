# Device dispatcher

Home PCs run a headless Grok session when a dispatcher (the Grok app, the car, or the CLI) submits a job. This service stores that queue in Mongo. Keycloak issues the tokens. The device daemon on each PC starts Grok. That daemon is the headless path in `java/device-daemon`. OpenBot connects to the same MCP server as grok.com, with client `freedriver-openbot` and role `device`.

Keycloak at `https://auth.freedriver.io/realms/freedriver` is the issuer. `%prod.quarkus.oidc.enabled` is true. The unprofiled property and the `%dev` and `%test` lines stay false. Anonymous callers receive 401, except the metadata GET below. A dispatcher token calls the dispatcher routes and must have `azp=freedriver-dispatcher`. A host token calls the host MCP tools and must have `azp=freedriver-openbot`. Host and dispatcher calls use `/dispatch/mcp` and `/mcp`.

Jobs, the host roster, and the in-flight submit lock are rows in the dashboard Mongo database. Assignments are the `agent-jobs` collection. Hosts are `agent-devices`. A restart reads those rows. All job state, the device roster, and submit locks are read from the `agent-jobs`, `agent-devices`, and `agent-locks` collections on every operation. Each state change is one conditional Mongo write, so two dispatcher processes cannot both claim or finish an assignment, and two submits for one subject cannot both take the lock. A submit wait, a job wait, and a device long-poll re-read the rows every 250 ms, rising to 1 s, until the deadline.

## Actors

| Actor | Role | Routes |
|---|---|---|
| Dispatcher | `dispatcher` | `GET /api/dispatcher/devices`, `POST /api/dispatcher/jobs`, `GET /api/dispatcher/jobs/{jobId}` |
| Host | `device` | `POST /api/dispatcher/host/report`, `/take`, `/jobs/{assignmentId}/start`, `/jobs/{assignmentId}/finish`; MCP tools `report_host` and `finish_job` on `/dispatch/mcp` until #540 |

The device id is the token subject. When the access token carries `device_id`, that claim wins. A dispatcher only reads jobs it submitted.

`POST /api/dispatcher/jobs` body:

```json
{"deviceIds":["pc-luna"],"agentName":"yuni","prompt":"say hello","channel":"TEXT"}
```

That sample is the headless Grok PC submit. The device registers `yuni`. An OpenBot job, which assumes the connector has reported Coder:

```json
{"deviceIds":["freedriver-openbot"],"agentName":"Coder","prompt":"say hello","channel":"TEXT"}
```

`channel` is `TEXT` or `SPEECH`. One assignment is queued per device. `agentName` must be one that device registered, or the call fails immediately and nothing is queued. The call stays open until every assignment is `succeeded`, `failed`, or `expired`, or 75 seconds pass. At that deadline, non-terminal assignments for the job move to `expired`, and a later claim is rejected. When the assignment is queued, and `FREEDRIVER_DISPATCHER_OPENBOT_WEBHOOK_SECRET` is set, the service POSTs a signed webhook to the OpenBot `dispatch-jobs` routine. The JSON body is the event type, the time, and the hostname. It does not include the prompt or the secret. An unset secret skips that POST, and the job still queues. The wait stays 75 seconds. A second submit for the same dispatcher subject is rejected while one submit is still in flight.

Assignment states: `queued` → `claimed` → `running` → `succeeded` | `failed`. `expired` is set at the submit deadline, and a device may also set it from any non-terminal state. `running` records `grokSessionId` when the device sends one. The Grok daemon sends a session id. OpenBot posts the result with the MCP tool `finish_job`. `finish` and the host route's `finishIfOpen` move an assignment to `succeeded` or `failed` from any open state: `queued`, `claimed`, or `running`. A refusal before work is one example of `failed` from `claimed`. A device only sees and updates its own assignments. `AssignmentView` carries `channel` and `prompt` for the owning device's assignment. A read by any other device is forbidden. The host reads queued work from `report_host`.

## Taking a job

A host program uses `HostApi` (`java/agent-dispatcher-api`), JSON in and out, role `device`. It publishes its roster, takes each job exactly once, says where it runs, and posts its result. Each call reads and moves only the caller's own assignments; the device id comes from the token. The paths are constants in `HostPaths` (`java/agent-dispatcher-model`), beside the request records, so the plain-Java connector uses the same ones.

| Route under `/api/dispatcher/host` | Body | Result |
| --- | --- | --- |
| `POST /report` | `HostReport`: `hostname`, `bots` (1 to 32 `ReportedBot`) | `DeviceView` |
| `POST /take` | `TakeRequest`: `waitSeconds` 0 to 50; `holding`, at most 64 assignment ids, optional | list of `AssignmentView` |
| `POST /jobs/{assignmentId}/start` | `StartRequest`: `deliveryRef`, 1 to 128 printable ASCII characters, no space | `AssignmentView` |
| `POST /jobs/{assignmentId}/finish` | `FinishRequest`: `succeeded`; `note`, at most 2,000 characters, optional | `AssignmentView` |

Refusals: 400 for a bad body, 403 for another device's assignment, 404 for an unknown one, 409 for a state the call does not start from, except finish: a finish on an assignment already `SUCCEEDED`, `FAILED` or `EXPIRED` answers 200 with the stored assignment and changes nothing, so the connector's backstop cannot replace the agent's result. Anonymous is 401, and a token whose client id and role do not pair is 403.

`take`, for the caller's device, in this order:

1. Every open assignment named in `holding` gets `heldUntil = now + host-lease`.
2. Every `QUEUED` assignment older than `take-within` becomes `EXPIRED` with note `no host took it`.
3. Every other `QUEUED` assignment becomes `CLAIMED` with `heldUntil = now + host-lease`, and every `CLAIMED` or `RUNNING` assignment outside `holding` whose `heldUntil` is past or absent gets a new `heldUntil`. Each is one conditional `findOneAndUpdate`, and the reply holds only the rows a write matched, so two replicas or two calls hand each job to one caller.
4. When nothing was returned, steps 2 and 3 repeat on the store's re-read schedule (250 ms, doubling to 1 s) until `waitSeconds` have passed.

`start` moves `CLAIMED` to `RUNNING`, stores `deliveryRef`, and renews `heldUntil`. The same call again on a `RUNNING` assignment with the same `deliveryRef` returns it unchanged. Another `deliveryRef` is a conflict, and another device's assignment is refused. `AssignmentView.deliveryRef` is null until `start` sets it. `report` is the store's `report`, and `finish` is the store's `finishIfOpen`.

Lease and expiry: `freedriver.dispatcher.host-lease` is 90 seconds and `freedriver.dispatcher.take-within` is 10 minutes. Start-up fails when `take-within` is under one second, and when `host-lease` is 50 seconds or less, the longest `take` wait, so a host that names its jobs in `holding` on every take keeps them. A job whose host stops taking is handed out again once its lease has passed, with its state and `deliveryRef`. The dispatcher logs one INFO line per returned job and per `start`: assignment id, device id, state, and `ageMs` since the job was stored.

## Dispatch connector

The device daemon in OpenBot mode (`"mode": "openbot"` in its config) is the dispatch connector of the OpenBot host. It takes that host's jobs through the four routes above, puts each prompt into the named agent's queue through OpenBot's Local scripts API, and watches the delivery until the turn ends. The agent posts its own result with `finish_job` of `freedriver-openbot` on `https://app.freedriver.io/dispatch/mcp`. The connector posts `finish` only with `succeeded` false, for a job it refused or a turn that ended with the job still open. `OpenBotWorker` holds those rules against two ports, `HostJobs` (the dispatcher, `HttpsHostJobs`) and `AgentHost` (OpenBot, `ScriptsAgentHost`).

Config: `deviceId` (always `freedriver-openbot`), `hostname`, `agents`, `secretFile`, `mode`, and `automationDir`, which defaults to `$XDG_CONFIG_HOME/OpenBot/automation`, else `~/.config/OpenBot/automation`. `agents` holds at most 32 names of at most 64 characters each, two names that differ only in case stop the start, and a name may contain spaces. `openbot-dispatcher-worker.json.example` and the user unit `freedriver-openbot-connector.service` are in the module. The unit runs as the OS user that runs OpenBot, and its command line holds only `--config`.

Dispatcher side. `HttpsHostJobs` sends only to the four `HostPaths` routes under `https://app.freedriver.io/api/dispatcher/host/` and to the fixed Keycloak token endpoint, with the client-credentials token of `freedriver-openbot` from the secret file. Paths with a dot segment or an encoded dot or slash are refused before the allow-list is read, and a request outside the list is refused before it is sent. The Grok-mode client keeps its own list under `/api/device/`. A 401 fetches a new token and repeats the call once. A take waits 50 seconds, with a timeout of 60, and names every job the connector holds, at most 64, so their holds renew inside the 90 second lease. A take that returns more new jobs than the room under 64 finishes the excess as failed (`the connector already holds 64 jobs`).

OpenBot side. `ScriptsAgentHost` reads `url` and `token` from the automation folder, follows no symlink for either file, and reads both again after a refused connection or a 401, because OpenBot writes new ones at each start and deletes them when it quits. The `url` is accepted only with scheme `http` or `https`, no user-info, query or fragment, and a host whose every address is loopback. Its JDK client follows no redirect and sends only the Local scripts token. It calls `GET /v1/agents`, `POST /v1/agents/{id}/messages`, and `GET /v1/agents/{id}/deliveries/{deliveryId}`.

Roster. The agents that take dispatch jobs are PM, Coder, Architect, TechOps, Security, Dispatcher, and Sysadmin. `openbot-dispatcher-worker.json.example` lists those seven. At start and every 30 seconds the connector reports each configured agent that OpenBot lists under the same name without regard to case, spelled as OpenBot spells it. OpenBot is the source of each name's spelling. A change of case only in OpenBot needs nothing else, because the connector matches its configured names ignoring case. Any other rename has to be made in the installed connector's agents setting too (`%h/.config/freedriver/openbot-dispatcher-worker.json`), and `freedriver-openbot-connector.service` restarted, because the connector reads that file once at start. Until then that agent leaves the roster: a new job for it is refused at enqueue with unknown agent, and a job already queued under the old name fails with agent is not listed by OpenBot. Two OpenBot agents with one such name are both left out. A bot is `busy` while the connector holds a job for it, else `idle`, and its activity is empty. With no configured agent listed, the connector skips that report. The live `list_agents` stays whatever `report_host` wrote last until #539 turns the heartbeat and dispatch-jobs routines off.

A job, step by step:

1. A `CLAIMED` job that is not `TEXT`, has a blank prompt, or names an agent that resolves to no single listed agent is finished as failed with that reason, and nothing is sent.
2. Otherwise one message goes to the agent, with the assignment id as `clientMessageId`. Its text is a fixed instruction (call `finish_job` of `freedriver-openbot` with this assignment id, `succeeded` and the reply as `note` before the turn ends, since a turn that ends without it fails the job), a delimiter line, and then the prompt unchanged.
3. A 4xx other than 401 from the message call finishes the job as failed with OpenBot's `error` text: Local scripts off for the agent (403), the hourly limit (429), a message that is too large (413). A receipt with no delivery, or a delivery id outside `StartRequest.DELIVERY_REF`, also fails the job. A timeout, a 5xx or a lost answer after the request was written fails the job and the message is not sent again.
4. Every 2 seconds the connector reads the delivery. `queued` and `starting` leave the job `CLAIMED`. The first `running` posts `start` with the delivery id, once.
5. `completed`, `failed`, `interrupted`, `cancelled`, or a 404 on the read means the turn has ended. The connector posts `finish` with `succeeded` false and `the turn ended without a result (<status>)`. When the agent had finished the job first, the route answers with that stored result, which stands. The connector stops holding the job once `finish` answers with a finished state. A 409 from `finish` keeps the job held, and `finish` is posted again on the next pass.
6. Any other delivery status keeps the job held and is logged once.

A job runs as long as the agent's turn, with no local timeout. A job handed back `RUNNING` after a restart is watched through its `deliveryRef` and is not sent again. A 409 from `start` keeps the job held and watched, with no second `start`. While OpenBot cannot be reached, or the dispatcher is down, jobs stay held and the calls repeat: every 2 seconds for the dispatcher and the delivery reads. The process stays up through both, also at start.

Notes and logs. Every failure note goes through `Notes.forUpdate` with the client secret, the raw secret file, the access token and the Local scripts token, and is cut to 2,000 characters after that. Log lines name an assignment id and a reason class, never a prompt, a note or a secret. The connector listens on nothing.

Repeated `clientMessageId`. OpenBot's `docs/automation.md` at tag `v0.72.0`, the build the host ran on 2026-11-15, says: "Keep `clientMessageId` (1–128 characters) stable when you retry the same message. The normal queue returns the first receipt for that agent and key for 24 hours, including after a restart." So a connector that stops between the message call and `start` gets the first delivery back for that assignment after its restart, and the agent receives the prompt once. Past those 24 hours, or on a build without that rule, the same key would be a second message. A receipt whose delivery id differs from the one the connector already holds for that job fails the job, and that second delivery is never started.

## Deploy

Compose service `agent-dispatcher` has no host port. On `app.freedriver.io`, Caddy sends `/mcp`, `/mcp/*`, `/dispatch/mcp`, `/dispatch/mcp/*`, `/api/dispatcher`, and `/api/dispatcher/*` to `agent-dispatcher:8080`. `/autonomy/mcp` and `/api/autonomy` go to `autonomy-mcp:8080`. Every other path stays on `dashboard:8080`.

`/dispatch/mcp` is the Quarkus MCP server. `/mcp` is the same tools. Role `dispatcher` sees `list_agents`, `openbot_send_prompt`, `openbot_await_turn`, and `get_job`. Role `device` sees `report_host` and `finish_job`. They call this same queue. The server's SSE paths `/mcp/sse` and `/dispatch/mcp/sse` use the same bearer check. A session id is bound to the bearer token subject and is not itself a credential. That binding is the Redis key `freedriver:mcp:dispatcher:` plus the session id, and the key expires 24 hours after it is stored. The binding is shared; the session is not. Another dispatcher process accepts the binding but answers 404 for a session it did not open, which is why a client holding a session is pinned (#547). Anonymous `GET` and `POST` on `/dispatch/mcp` and `/mcp` receive 401 with `WWW-Authenticate: Bearer` and `resource_metadata="https://app.freedriver.io/api/dispatcher/oauth-protected-resource"`, and they do not run a tool. A token whose client id and role do not pair receives 403. The constraints on each tool argument are the validation and the advertised input schema; a bad argument is JSON-RPC error -32602 and an argument the tool does not declare is ignored. A call without the tool's role is JSON-RPC error -32005. The metadata document, the bearer challenge, and the session binding are `java/mcp-support`, shared with the autonomy MCP server. The same sticky-routing note as the autonomy server applies: a second replica uses Caddy cookie `mcp_dispatcher`, then the `Authorization` header, then round_robin. A client that calls without a session, at `MCP-Protocol-Version` `2026-07-28` with `Mcp-Method` on every request as the agents on the OpenBot host do, is answered by any replica and keeps working through a restart or a deploy. A client that holds a session, at `2025-11-25` as grok.com does, stays on one replica by the cookie or by its bearer, and loses that session when that replica restarts (#547).

`GET /api/dispatcher/oauth-protected-resource` is the only unauthenticated dispatcher response. It is OAuth protected-resource metadata and nothing else: `resource` is `https://app.freedriver.io/dispatch/mcp`, `authorization_servers` is only `https://auth.freedriver.io/realms/freedriver`, and `bearer_methods_supported` is `header`. The document has no client secret and no devices, jobs, or prompts. `/dispatch/mcp`, `/mcp`, and other dispatcher routes stay authenticated.

The device daemon in `java/device-daemon/` runs on the PC in Grok mode. It registers, heartbeats, long-polls, claims, and starts one headless `grok` process per winning text claim. The tool allowlist is local configuration and defaults to no tools. The prompt is written to a mode `0600` file and passed with `--prompt-file`. Grok mode still calls `https://app.freedriver.io/api/device/*`, and this service answers those URLs with 404. OpenBot mode is the dispatch connector above. A user systemd unit in the module is what #213 installs on the PC. The local session timeout kills that child process. The 75 second queue deadline stays in `JobStoreService`, the Mongo implementation of `JobStore`.

A queued job notifies the OpenBot routine `dispatch-jobs`. That routine calls `/dispatch/mcp` with client `freedriver-openbot`. `report_host` publishes each bot's name, whether it is idle or busy, and a short activity note, and the reply is this host's jobs whose status is `QUEUED`. The routine routes `agentName` to the named agent, then `finish_job` posts the result. grok.com keeps client `freedriver-dispatcher` and the tools `list_agents`, `openbot_send_prompt`, `openbot_await_turn`, and `get_job`. `openbot_send_prompt` writes the job to Mongo and returns the job id. It does not wait for OpenBot. Another thread POSTs the `dispatch-jobs` webhook. Optional `on_busy` is `supersede` or `queue`. Omit it, or pass null, and the stored value is `supersede`. Anything else is rejected. The value is stored on the `agent-jobs` row before that webhook runs, and `report_host` returns it with each job whose status is `QUEUED`. `GET /api/jobs` returns it as `on_busy` on each row. The webhook itself does not change. `openbot_await_turn` takes that job id and `delaySeconds`, at most 120. It returns when the job is done, or when that delay elapses, and a timeout does not expire the job. More than 120 seconds is rejected. `get_job` reads the job without waiting. The REST call above still waits 75 seconds. `GET /api/jobs` lists every caller's assignments, newest first, for a portal-admin session, the same session as `/api/phones`. The dashboard reads them from the dispatcher's `GET /api/dispatcher/admin/jobs` as the service account `freedriver-portal-jobs`, whose token carries realm role `dispatcher-admin`; the dispatcher accepts that client only with that role. That path is on the compose network only; Caddy answers 404 for `/api/dispatcher/admin` from outside. Each row is an `AssignmentView`. The Agent jobs page is `/agent-jobs`.

The address of that webhook is the setting `FREEDRIVER_DISPATCHER_OPENBOT_WEBHOOK_URL`, read as `freedriver.dispatcher.openbot-webhook-url`. Its default is the address compiled into the dispatcher, `https://signal.openbot.run/v1/webhooks/0ca403fc-5874-407c-8e70-38c518d442ee`, and an unset, empty or white-space value keeps that default. The value is the whole address the dispatcher posts to, path included. A value that is set is `https`, with a host and without user-info; start-up refuses any other value, `http://127.0.0.1` and `http://localhost` included, with a configuration error that names `freedriver.dispatcher.openbot-webhook-url`. On the production host the value is written in `/opt/freedriver-secrets/.env` and applied by recreating `agent-dispatcher` only, from `/opt/freedriver-web`, with the Deploy workflow's compose command scoped to that service:

```
sudo -n /usr/bin/docker compose --env-file /opt/freedriver-secrets/.env --env-file .build-number.env -f docker-compose.yml -f docker-compose.ghcr.yml up -d --force-recreate --no-deps --no-build --pull never agent-dispatcher
```

A restart of the container keeps its old environment, so a changed value takes effect only through that recreate. A refused address stops the dispatcher before it listens: the container restarts in a loop and stays unhealthy, so `/mcp`, `/dispatch/mcp` and `/api/dispatcher` stay down until the value is fixed and the service is recreated. This setting is a stopgap that freedriver-web#540 removes together with the relay path.

## Keycloak

`scripts/provision-keycloak-freedriver.sh` can create the public client `freedriver-dispatcher` (authorization code + PKCE, claim `actor=dispatcher`, realm role `dispatcher`). That public client is the Grok connector. Anonymous client registration (DCR) Trusted Hosts are `grok.com`, `console.x.ai`, `x.ai`, and `*.x.ai`, so Grok Connect Apps can add `/dispatch/mcp` and `/autonomy/mcp` with a grok.com redirect. New clients use redirect URIs on those hosts. Keycloak matches those URIs. Grok's registration POST may come from xAI egress. Those DCR clients keep a limited role set. The roles client scope includes `mcp-user` and `dashboard`, so a grok.com DCR access token carries those roles when the signed-in user holds them. The OpenBot MCP client is the separate confidential client `freedriver-openbot`: authorization code + PKCE with redirect `http://127.0.0.1:28417/mcp-auth` for OpenBot Sign in, plus client credentials, realm role `device`, for `/dispatch/mcp`. `ensure_openbot_mcp_client` runs after `ensure_device_client` so other device ids stay client-credentials. Device clients for the leftover PC daemon are created when `FREEDRIVER_DEVICE_CLIENTS` lists their ids, or when that variable is unset and `/opt/freedriver-secrets/keycloak-device-clients.env` names them. Secrets go to `/opt/freedriver-secrets/` and stay out of the script output. Run that script on production as its own ops step.

Dashboard sign-in is the OIDC BFF against that same realm. Dispatcher and device clients get their tokens from Keycloak.
