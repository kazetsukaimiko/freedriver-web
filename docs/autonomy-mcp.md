# Autonomy MCP

Grok talks to house appliances over Streamable HTTP MCP at `https://app.freedriver.io/autonomy/mcp`. That URL is its own Quarkus process (`java/autonomy-mcp/`).

Keycloak at `https://auth.freedriver.io/realms/freedriver` is the issuer. The access token audience is `https://app.freedriver.io/autonomy/mcp`. Mapper `audience-autonomy-mcp` on `freedriver-grok-mcp` and grok.com Dynamic Client Registration clients puts that audience on the access token. Client scope `autonomy-mcp` is a realm default so a later grok.com registration gets it too. `azp` is the Keycloak client id: `freedriver-grok-mcp` for the public client, or the client id Keycloak assigned when grok.com registered through Dynamic Client Registration. `%prod.quarkus.oidc.enabled` is true. The unprofiled property and the `%dev` and `%test` lines stay false. Anonymous callers receive 401 with `WWW-Authenticate: Bearer resource_metadata="https://app.freedriver.io/api/autonomy/oauth-protected-resource"` and no login redirect. The grok.com Custom connector uses public client `freedriver-grok-mcp` (authorization code + PKCE S256) with redirect `https://grok.com/connectors-oauth-exchange-code/`.

The process is off unless compose sets `FREEDRIVER_AUTONOMY_MCP_ENABLED=true`. Off answers 404 on `/autonomy/mcp`. Live-commands remain a dashboard setting.

## Tools

| Tool | Roles | Dashboard call |
|---|---|---|
| `list_appliances` | `mcp-user` | `GET /api/mcp/appliances` |
| `home_status` | `mcp-user` | `GET /api/mcp/home-status` |
| `debug` | `mcp-user` and `mcp-debug` | `GET /api/mcp/debug` |
| `switch_appliances` | `mcp-user` and `dashboard` | `POST /api/appliances/{id}/{name}` per entry now, or `POST /api/mcp/scheduled-switches` per entry with `delaySeconds` |

The tools are `AutonomyTools` on the Quarkus MCP server (`quarkus-mcp-server-http`, root path `/autonomy/mcp`). A caller without `mcp-user` receives 403 on `/autonomy/mcp` before any tool. `switch_appliances` also requires `dashboard`, and `debug` requires `mcp-debug`; a call without the tool's role is JSON-RPC error -32005. The constraints on each tool argument are the validation and the advertised input schema. A bad argument, including a fraction, a quoted number, or a quoted boolean, is JSON-RPC error -32602 that names the argument or the constraint. Each tool takes only its declared arguments, and each `switch_appliances` entry only `applianceName`, `on`, and `delaySeconds`; any other argument or entry field is JSON-RPC error -32602 "invalid params" before the tool runs. The grok.com sign-in user is `kaze`; that account holds `mcp-user` and `dashboard`. After the bearer check, the process calls `http://dashboard:8080` as the connecting user. It exchanges the caller's access token at Keycloak (RFC 8693 token exchange) as the confidential client `freedriver-autonomy-mcp`, for a token with audience `freedriver-api`, the same `sub`, and only those of `mcp-user` and `dashboard` the caller holds. That token is the bearer on the dashboard call. The dashboard checks it in its `internal` OIDC tenant, which takes a bearer only on `/api/mcp` and `/api/appliances`, requires audience `freedriver-api` and `azp` `freedriver-autonomy-mcp`, and its own `@RolesAllowed` decides. No secret is shared between the two services. The exchanged token carries no `portal-admin` or `mcp-debug`: `debug` checks `mcp-debug` on the caller's own token, and the dashboard's debug route asks for `mcp-user`. When Keycloak refuses the exchange, the tool answers "That was refused." and no dashboard route is called. An immediate entry uses the portal command path and the live-commands gate, spends `appliances.commands`, and is audited as the portal subject. A delayed entry spends `appliances.schedules` and takes the pending cap. It is stored by `POST /api/mcp/scheduled-switches`, which checks the role, the schedule rules and `appliances.schedules`, without the live-commands gate and without the portal command path. The live-commands gate applies when the poller publishes the row through `ApplianceService.issueCommand`. A delayed entry can be refused with 429 when that caller's schedules window is full, and with an empty 429 when that subject already holds 30 pending rows (`freedriver.scheduled-switches.max-pending`). `switch_appliances` reports that entry as refused while entries already applied stay applied, so an immediate on can succeed while its paired delayed off is refused.

`switch_appliances` switches one or more named appliances of one house in one call. It takes `instanceId` and `appliances`, a list of 1 to 16 entries. Each entry is `applianceName` (1 to 64 characters), `on`, and optional `delaySeconds`, an integer from 0 through 86400; five minutes is 300. The tool description tells the model to put every appliance the person named into `appliances`, and to leave a light on for five minutes by adding it once with `on` true and once with `on` false and `delaySeconds` 300.

| Rule | Behaviour |
|---|---|
| Order | Entries run in list order, each as its own dashboard call. |
| Now or later | An entry without `delaySeconds`, or with 0, switches now and waits for the dashboard result. A positive delay posts the switch to the dashboard (`POST /api/mcp/scheduled-switches`) and that entry is done when the dashboard has stored it. |
| Same appliance twice | The same name with the same delay refuses the whole call before any entry runs. The same name with different delays runs both, for example on now and off in 5 minutes. |
| Tool rate limit | Each entry takes one of the caller's 30 calls per minute, all or none. A list longer than the calls left refuses the whole call, and the hits it took are given back. |
| Dashboard limits | An immediate entry spends `appliances.commands` on the portal command path, and the live-commands gate applies to that entry. A delayed entry spends `appliances.schedules` and takes the pending cap. It is stored by `POST /api/mcp/scheduled-switches`, which checks the role, the schedule rules and `appliances.schedules`, without the live-commands gate and without the portal command path. The live-commands gate applies when the poller publishes the row through `ApplianceService.issueCommand`. A delayed entry can be refused with 429 when the caller's schedules window is full, and with an empty 429 when that subject already holds 30 pending rows (`freedriver.scheduled-switches.max-pending`). `switch_appliances` reports that entry as refused while entries already applied stay applied, so an immediate on can succeed while its paired delayed off is refused. A refused entry is that entry's sentence, and the others still run. |
| Reply | One sentence per entry, in order, each naming its appliance: "Fridge turned on. Porch light: too many requests. Try again in a minute. Lamp will turn off in 5 minutes." The reply is a tool error when every entry was refused. |
| Audit | One line per entry with that entry's result (`allowed`, `scheduled`, `denied`, `rate-limited`, or `error`), including each entry of a refused call. |

The dashboard stores a delayed switch in the Mongo collection `scheduled-switches` by `POST /api/mcp/scheduled-switches`, which checks the role, the schedule rules and `appliances.schedules`, without the live-commands gate and without the portal command path. One subject can hold 30 pending rows (`freedriver.scheduled-switches.max-pending`). The next store is an empty 429 and stores nothing. Concurrent stores never take a subject over that cap, and when two race for the last slot both may be refused. Rows already stored still fire. A slot opens when a row is deleted, confirmed or given up after three attempts. A stored row fires when due through `ApplianceService.issueCommand` and spends neither `appliances.schedules` nor `appliances.commands`. The live-commands gate applies when the poller publishes the row through `ApplianceService.issueCommand`. One dashboard replica claims each due row. A confirmed row is deleted; a failed or timed-out command is tried again, up to three attempts. The row is audited as the user who scheduled it.

Rate limit is 30 calls per 60 seconds per subject per tool; each `switch_appliances` entry counts as one call. An immediate entry spends `appliances.commands` and a delayed entry spends `appliances.schedules` and takes the pending cap of 30 (`freedriver.scheduled-switches.max-pending`). A delayed entry is stored by `POST /api/mcp/scheduled-switches`, which checks the role, the schedule rules and `appliances.schedules`, without the live-commands gate and without the portal command path. The live-commands gate applies when the poller publishes the row through `ApplianceService.issueCommand`. A delayed entry can be refused with 429 when the caller's schedules window is full. `switch_appliances` reports that entry as refused while entries already applied stay applied, so an immediate on can succeed while its paired delayed off is refused. Spoken replies name appliances and omit instance ids.

`GET /api/autonomy/oauth-protected-resource` is the only unauthenticated autonomy response. It is OAuth protected-resource metadata. `/autonomy/mcp` requires a bearer. A session id names the bearer subject that opened it, and a different subject presenting it receives 403. That binding is the Redis key `freedriver:mcp:autonomy:` plus the session id, and the key expires 24 hours after it is stored. The binding is shared; the session is not. Another autonomy-mcp process accepts the binding but answers 404 for a session it did not open, which is why a client holding a session is pinned (#547).

The metadata document, the bearer challenge, the metadata permit policy, the audit line, and the session-to-subject binding are `java/mcp-support`, the library both MCP servers use. Each service sets `freedriver.mcp.resource`, `freedriver.mcp.authorization-servers`, `freedriver.mcp.metadata-path`, `freedriver.mcp.paths`, `freedriver.mcp.roles`, and `freedriver.mcp.session-prefix`.

## Deploy

Compose service `autonomy-mcp` has no host port. On `app.freedriver.io`, Caddy sends `/autonomy/mcp`, `/autonomy/mcp/*`, `/api/autonomy`, and `/api/autonomy/*` to `autonomy-mcp:8080`.

Compose loads `/opt/freedriver-secrets/keycloak-freedriver-autonomy-mcp.env` into `autonomy-mcp`. `scripts/provision-keycloak-freedriver.sh` creates the client `freedriver-autonomy-mcp` and writes `FREEDRIVER_AUTONOMY_MCP_CLIENT_SECRET` to that file once. Run the script on the live realm before the release that carries the token exchange. Until the client and the file exist, every tool that calls the dashboard is refused.

A Streamable HTTP session keeps state in the process that opened it, so a second replica uses Caddy stickiness on the MCP reverse_proxy: cookie `mcp_autonomy`, then the `Authorization` header, then round_robin. A client that stores the cookie stays on that replica. A client that does not store it is pinned by its bearer until that token is renewed (#547). A client that calls without a session, at `MCP-Protocol-Version` `2026-07-28` with `Mcp-Method` on every request as the agents on the OpenBot host do, is answered by any replica and keeps working through a restart or a deploy. A client that holds a session, at `2025-11-25` as grok.com does, stays on one replica by the cookie or by its bearer, and loses that session when that replica restarts (#547).
